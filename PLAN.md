# Plan

Status: scoping, nothing built beyond the input-capture scaffold in
`deploy.yml`. This repo owns the full pipeline end to end — fetch, build,
test, publish, deploy — copying whatever logic it needs out of a target
repo rather than calling back into that repo's own CI/CD. **PoC: this repo
must never modify a target repo.** Read-only checkout only; nothing is
committed or pushed anywhere but here and the image registry.

First real target: `Attom-AI/attogen`'s two independently-deployable
services (converter, pipeline). Everything below is scoped against that
concrete case, generalized later once it works once.

## Pipeline shape

```
inputs (repo, branch, service, environment)
  -> fetch (checkout target repo at branch)
  -> build + test
  -> build image(s), publish
  -> deploy
```

## 1. Inputs

| Input | Shape | Notes |
|---|---|---|
| `repo` | string | exists today in `deploy.yml` |
| `branch` | string | exists today in `deploy.yml` |
| `service` | `type: choice`, `[converter, pipeline]` (multi, or run twice) | **New, and load-bearing.** Confirmed against `attogen`: converter and pipeline are separately built and separately deployed already (`build-image.yml` builds them as two distinct images from two distinct Dockerfiles; `deploy-k3s.yml` rolls each independently and either can be absent from a release). So `service` isn't a convenience input, it's what scopes stage 2 and 3 to the right Dockerfile/build context. |
| `environment` | `type: choice`, `[k3s]` for now | Deliberately constrained to one option today so the shape exists without pretending Render/Azure are implemented. Adding an option later should mean adding a branch in stage 4, not redesigning the input. |

## 2. Fetch

Cross-repo checkout of `repo`@`branch`. Needs a credential — `GITHUB_TOKEN`
is scoped to this repo only and can't read `attogen`.

**Open decision:** a fine-grained PAT (`ATTOGEN_READ_TOKEN`, contents:
read-only on `attogen`) — not yet created. Per the earlier conversation,
this should be generated and set by whoever owns the credential
(`gh secret set ATTOGEN_READ_TOKEN -R ezekiel-atl/k3s-deploy-tool`), not
generated by an agent.

## 3. Build + test

**Open decision, worth resolving before copying anything:** `attogen`'s
`ci.yml` `test` job runs the **full Django suite** — WeasyPrint/Pango
system deps, the whole `Pipfile`, `pytest` with coverage — none of which
converter/pipeline need. `deployment-converter.yaml`'s own comment is
explicit about this: the converter image "deliberately does not share
`.config/k3s/Dockerfile`'s `deps` stage — that stage installs the whole
Pipfile... for ~1.3 GB of libraries this service never imports." So copying
`ci.yml`'s `test` job wholesale would test the wrong thing at the wrong
weight. The right-sized version is whatever test coverage exists scoped to
`services/document_conversion/` and `services/opportunity_pipeline/`
specifically — each has its own `requirements.txt`, not `Pipfile`.
Checked directly: the two aren't symmetric. `services/opportunity_pipeline/`
has a `tests/` directory; `services/document_conversion/` has **no
dedicated tests directory at all**. So "build + test" can't be one uniform
step across both services — pipeline gets real test execution, converter's
stage would currently be build-only (or "test" means something looser for
it, like a smoke-run of `app.py`) until/unless tests are added there.

## 4. Build image(s), publish

Copy the per-service build steps from `build-image.yml` — `docker build`
against `services/document_conversion/Dockerfile` or
`services/opportunity_pipeline/Dockerfile`, scoped to whichever `service`
input(s) were selected.

**Open decision: which registry.** `attogen` publishes to
`ghcr.io/attom-ai/forgen`, an org-owned package namespace — pushing there
would need write access to `Attom-AI`'s packages, the same permission class
that refused repo creation earlier. For a PoC under a personal account, the
natural target is `ghcr.io/ezekiel-atl/...` instead. Worth flagging now
because it has a real consequence for stage 5: the live cluster's
Deployments pull from `ghcr.io/attom-ai/forgen` today, so an image
published under a different namespace can prove the build works but can't
be rolled onto the real cluster without either push access to the org
namespace or a cluster-side change to pull from a second registry (the
second of which starts to brush up against "don't touch the target"
territory if "target" is read broadly as the cluster, not just the repo).

## 5. Deploy

Copy the relevant `kubectl` sequence from `deploy-k3s.yml` (image set,
rollout status, health check), scoped to `environment: k3s` for now.

**Same blocking unknown as in the proposal doc, still unresolved:**
`deploy-k3s.yml` requires a **self-hosted runner** on the cluster's private
network (`[self-hosted, linux, k3s]`). Whether that runner is registered at
the `Attom-AI` **organization** level (reachable from a separate repo like
this one) or scoped only to `attogen`'s own repository (not reachable from
here at all) — still can't be checked from this session (needs org-admin;
got a 403 earlier). This is the one item that could block stage 5 entirely
regardless of how well the rest of the pipeline is built. Worth getting a
definite answer before investing in the deploy stage specifically.

## What's deliberately not in scope yet

- Render/Azure as real `environment` options — the input allows for it
  later; nothing implements it now.
- Any write path back to `attogen` or any other target repo.
- Reusing `attogen`'s own `build-image.yml`/`deploy-k3s.yml` by calling
  them (that was Option A in the proposal doc; this plan is Option B —
  own the pipeline, copy the logic, per Ezekiel's direction).

## Next step

Resolve the registry and runner-reachability questions above (4 and 5) —
both are permission/access questions for whoever holds org-admin, not
engineering work — since they determine whether stages 4 and 5 can be
built as real, testable steps or only sketched. Stages 1–3 don't depend on
either and could be scoped/built independently in the meantime.
